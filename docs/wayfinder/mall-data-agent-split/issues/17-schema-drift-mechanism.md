# 17: schema 漂移检测与商户库迁移机制

Type: grilling
Status: resolved

## Question

08 号 D2 已定方向「静态 schema 卡片 + 启动期/CI 漂移断言」，本票定机制细节（02 号研究票建议的独立后续票，fog 毕业）：

- 断言形态：启动期 `inspect` diff（SQLAlchemy introspection vs 代码事实源）vs CI 期对比 vs 双者都要；
- 商户库要不要上 alembic：现状是 `_MERCHANT_DDL` 幂等字符串启动重放，`IF NOT EXISTS` 只增不删改——删列/改型语义怎么办（迁移脚本化 vs 显式运维手册）；
- 断言失败的处理：拒绝启动 / 降级告警继续跑（商户数据分析面 vs 核心链路的容错差异）；
- schema 卡片生成器与本机制的耦合方式（02 号建议：卡片生成不阻塞本票，漂移断言接入依赖本票决议）。

## Answer

决议日期 2026-09-17，用户全盘采纳推荐（Q1–Q4）。

### D1 断言形态 = 双层

- **CI 期强断言**：流水线起临时 postgres，重放 `_MERCHANT_DDL` + 跑 engine alembic，再 `inspect` 对比代码事实源生成的期望 schema，不一致直接红——漂移拦在合并前。
- **启动期轻检查**：gateway/engine 启动时对真实库 inspect vs 代码卡片指纹，覆盖 CI 拦不住的「手工改生产库」。

### D2 商户库迁移 = v1 不上 alembic

7 表小 schema、单库单部署，幂等 DDL 重放 + D1 断言已够。删列/改型走**手册式流程**：显式迁移 SQL 文件（入仓可审计）+ 同步更新 `_MERCHANT_DDL` 字符串 + CI 断言护栏。alembic 化留二期，触发 = 商户库频繁演化或多部署形态出现。

### D3 失败处理 = 分面容错

- **核心链路只告警不阻塞**：schema 漂移不挡商户做生意，告警进观测面。
- **数据分析面主动降级**：data agent 启动/查询前校验卡片指纹 vs 实库，不一致即诚实拒绝（「数据结构变更中，分析暂不可用」），绝不在漂移 schema 上算指标出数。

### D4 与卡片生成器解耦

卡片生成器只读代码事实源（编译期产物，无运行时依赖）；漂移断言器独立模块，比对「卡片指纹 vs inspect 实况」；二者只共享事实源定义，互不阻塞。
